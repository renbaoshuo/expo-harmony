# @expo-harmony/template

Bare HarmonyOS native template for Expo SDK 55, React Native 0.84.1, and RNOH
0.84.1. It is consumed by Expo prebuild:

```sh
npx expo prebuild --platform harmony --template @expo-harmony/template
```

Application-specific values are placeholders only; the
`@expo-harmony/prebuild-config` mod chain owns the final output. Signing keys,
passwords, absolute paths, OHPM caches, bundles, and HAP files are never
shipped in this template.

The template is intentionally minimal. Its package manifest contains only the
Core and Harmony build prerequisites; it does not install Expo feature modules
or the autolinking tool as application dependencies. Applications add the
official JavaScript package and its `@expo-harmony/*` native carrier only when
they use that feature. The Harmony autolinker then discovers the installed
carriers during prebuild.

The template does not hard-code a path into the application's `node_modules`.
The RNOH Hvigor plugin dependency is injected by
`@expo-harmony/prebuild-config` from the project's installed
`@react-native-oh/react-native-harmony-cli` package during prebuild.
The native HAR input fingerprint is generated by the template's local
Hvigor helper, so the template does not import `@expo-harmony/cli`.

The native asset package deliberately does not depend on optional runtime
carriers. This keeps Expo's normal template dependency reconciliation from
reinstalling Linking, Splash Screen, System UI, Application, or community
navigation packages after an application removes them. When an application
uses Router, it explicitly installs official `expo-router` alongside
`@expo-harmony/expo-router`. The latter owns the SDK/RNOH native dependency
composition and supplies package-level sidecar metadata for vendor HARs that do
not yet declare autolinking themselves. Non-Router applications do not install
that carrier or its stack. A separate adapter remains only when the repository
actually patches JavaScript or native ABI, as it currently does for Screens.

The placeholder EntryAbility is exported because it owns the launcher and
deep-link skills and must also be startable through HarmonyOS's `aa` tool.
Prebuild keeps that managed entry Ability exported after identity changes.
EntryAbility and Index are canonical inputs for full-file generation and remain
module-neutral. They import only Expo Modules Core and the autolinking-generated
Harmony host Provider; optional modules are represented by semantic subscriber,
listener, and root-component declarations rather than source-code insertion
markers.

Install `@expo-harmony/prebuild-config` directly in the application that
registers it in `expo.plugins`. The template is the canonical native asset
package consumed by that plugin; it deliberately does not depend back on the
plugin, so the two publishable packages do not form an installation cycle.
The application must also keep `@expo-harmony/cli` installed: generated release
Hvigor tasks call its project-local `export:embed` binary, and never fall back
to a global Expo, React Native, or Harmony CLI.

Building requires OHPM, Hvigor, a compatible HarmonyOS SDK/NDK, and Node.js
20+ for the release Metro task. `EXPO_HARMONY_NODE` can explicitly select the
Node executable. Keep the application path free of spaces until the upstream
Harmony CMake summary generator quotes absolute paths.

Debug loads JavaScript from Metro. Release loads `hermes_bundle.hbc` through a
small `ResourceJSBundleProvider` subclass that copies the exact raw-resource
view into an aligned `ArrayBuffer`. This avoids RNOH 0.84.1's mmap/HAP-entry
alignment failure while retaining its public bundle-provider contract.

The release task has one `@ExpoHarmonyBundle` owner between resource processing
and compilation. A normal DevEco/Hvigor build invokes `expo-harmony
export:embed`; `expo-harmony run --variant release` pre-exports the same
validated artifact and sets an internal validation-only marker so Hvigor does
not bundle twice.

The generated `harmony/build-profile.json5` is ignored by Git because an
external `harmony.signingConfigFile` is merged into it for local builds. Never
commit that generated profile or its source signing material.
